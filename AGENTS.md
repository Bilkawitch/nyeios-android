## 2. Механизм аутентификации и сессии

### 2.1 Точка входа и параметры запроса
- **URL авторизации:** `https://eios.gukolomna.ru/index.php?login=yes`
- **HTTP-метод:** `POST`
- **Content-Type:** `application/x-www-form-urlencoded`
- **Обязательные поля формы:**
  - `AUTH_FORM=Y`
  - `TYPE=AUTH`
  - `USER_LOGIN=<логин или email>`
  - `USER_PASSWORD=<пароль>`
  - `USER_REMEMBER=Y` (для сохранения длительной сессии)
  - `backurl=/eios/` (целевой адрес перенаправления после входа)

### 2.2 Жизненный цикл сессии и Cookie
1. **Успешный вход:**
   - Сервер возвращает `302 Found` с редиректом на `backurl`.
   - В заголовках `Set-Cookie` возвращается набор куки, из которых ключевыми являются:
     - `PHPSESSID` — идентификатор PHP-сессии (`HttpOnly`, `Path=/`).
     - `BITRIX_SM_UIDH` — **32-символьный хэш авторизации пользователя**. Является главным маркером успешной аутентификации. Если этот маркер не выставлен — сессия считается анонимной.
     - `BITRIX_SM_UIDL` — URL-encoded логин пользователя (например, `user%40example.com`).
     - `BITRIX_SM_GUEST_ID` — числовой ID гостя в системе веб-аналитики Битрикса.
     - `BITRIX_SM_LAST_VISIT` — временная метка последнего визита.
     - `BITRIX_SM_TIME_ZONE=-180` — часовой пояс (UTC+3, московское время).
     - `BITRIX_CONVERSION_CONTEXT_s1` — сериализованный контекст конверсий.
2. **Неверные учетные данные:**
   - Сервер возвращает HTTP `200 OK` (не 401/403!), содержащий ту же HTML-страницу авторизации.
   - В теле ответа присутствует текст ошибки `Неверный логин или пароль портала ЭИОС`.
   - Выставляется HTTP-заголовок `X-Bitrix-Ajax-Status: Authorize`.
   - Кука `BITRIX_SM_UIDH` **не выставляется**.
3. **Требование к обработке редиректов:**
   - Клиент обязан сохранять куки со всех промежуточных 302-ответов (например, через `CookieJar` с просмотром цепочки `priorResponse`). Потеря кук на промежуточном шаге приводит к разрыву сессии.

## 4. Структура HTML и парсинг данных

### 4.1 Расписание (`/eios/contacts/timetable/`)
- **Корневая таблица:** `<table class="schedule-table">`.
- **Дни недели:** извлекаются из заголовка `thead > tr > th[1..6]` («Понедельник», «Вторник», «Среда», «Четверг», «Пятница», «Суббота»).
- **Временные слоты (Пары):**
  - Первая колонка каждой строки `tbody > tr > td[0]` содержит текст времени (например, `08:30 - 10:00`, `10:15 - 11:45`, `12:15 - 13:45`, `14:00 - 15:30`, `15:45 - 17:15`, `17:30 - 19:00`).
- **Ячейки занятий:**
  - Внутри ячейки дня располагаются вложенные таблицы `<table class="schedule-cell">`.
  - Строка подгруппы: `<tr class="schedule-cell-subgroup">` содержит текст подгруппы (например, `1 подгруппа`).
  - Строки данных с 2 ячейками:
    - Правая ячейка (`td[1]`) содержит либо аудиторию (если есть цифры или ключевые слова `ДО`, `ДОТ`, `ЭОР`), либо тип занятия («Практика», «Лекция», «Лабораторная»).
    - Левая ячейка (`td[0]`) содержит название дисциплины (если справа аудитория) либо ФИО преподавателя (если справа тип занятия).

### 4.2 Живая лента (`/eios/contacts/personal/user/<id>/`)
- **Контейнеры постов:** селекторы `.feed-post-block` или `.log-entry`.
- **Идентификатор поста:** атрибут `id` (например, `blg-post-38666` или `BLOG_10416-39139`).
- **Автор:** элементы с классами `.feed-post-user-name`, `.user-name` или `.author`.
- **Целевая аудитория (Группа):** элемент `.feed-add-post-destination-new` или `.destination` (например, `23АН-о-41`).
- **Дата и время:** элементы `.feed-time` или `.feed-post-time` (форматы: `сегодня, 11:52`, `вчера, 10:53`, `09.09 10:01`).
- **Текст объявления:** `.feed-post-text` или `.feed-post-contentview` / `.feed-post-text-block-inner`.
- **Прикрепленные документы:** ссылки `<a>` с расширениями `.pdf`, `.docx`, `.doc`, `.xlsx` или путями `/files/element/historyget/`.

## 5. Архитектурные проблемы и причины экстремальной медлительности портала

1. **DOM Bloat:** Страница живой ленты весит 7.5+ МБ и содержит до 10 000 узлов DOM из-за табличной верстки с 15-кратной вложенностью.
2. **Asset Overhead:** 42 CSS-файла и 138 JS-скриптов блокируют рендеринг и вызывают многочисленные перерасчеты стилей.
3. **Отсутствие REST API:** Все данные приходится извлекать через парсинг «сырого» HTML (`jsoup`).
4. **Нестабильность под нагрузкой:** Утренние сбои `HTTP 504 Gateway Timeout` из-за перегрузки PHP 7.2 / MySQL.

## 6. Подсистема интерактивной векторной карты этажей и indoor-навигации

Подсистема поэтажной навигации предназначена для ориентирования студентов в главном корпусе ГСГУ. При нажатии на номер аудитории в карточке занятия открывается интерактивная схема этажа с позиционированием аудитории и возможностью построения пешеходного маршрута между последовательными парами.

### 6.1 Координатная система и масштабирование
- **Базовая координатная сетка:** `1005 × 605` пикселей (пропорции реального плана 4 этажа главного корпуса).
- **Масштаб расстояний:** 1 пиксель ≈ 0.11 метра.
- **Подложка:** Очищенное растровое изображение плана этажа в прозрачном PNG ([floor_4.png](file:///d:/NyA-N/eios-schedule-android/app/src/main/res/drawable-nodpi/floor_4.png)).

### 6.2 Формат модели данных (JSON Schema)
Схема этажа сериализуется в JSON-файл ([floor_4_map.json](file:///d:/NyA-N/eios-schedule-android/app/src/main/assets/floor_4_map.json)), включающий:
```json

  "height": 605,
  "corridors": {
    "horizontalY": 492,
    "verticalX": 902,
    "junction": { "x": 902, "y": 492 }
  },
  "stairs": [
    { "id": "west", "name": "Западная лестница", "x": 212.8, "y": 461.4 },
    { "id": "central", "name": "Центральная лестница", "x": 602.5, "y": 450.0 },
    { "id": "east", "name": "Восточная лестница", "x": 866.1, "y": 443.9 }

        { "x": 115, "y": 492 }

      "stairs": "Западная лестница"
    }

```

### 6.3 Топология коридорного графа
На 4 этаже выделены 3 опорные коридорные оси:
1. **Главный горизонтальный коридор:** ось `y = 492.0` (от `x = 115` до `x = 902`).
2. **Восточный вертикальный коридор:** ось `x = 902.0` (от `y = 80` до `y = 492`).
3. **Западное вертикальное крыло:** ось `x = 115.0` (от `y = 340` до `y = 492`).

### 6.4 Принципы трассировки от двери к двери (Door-to-Door Routing)
- **Точка старта и финиша:** Маршруты строятся строго от координат двери исходного помещения `doorPoint = Offset(doorX, doorY)` до двери целевого помещения.
- **Внутрикрыльевая навигация (Intra-wing optimization):**
  - При перемещении между аудиториями одного крыла (например, 433 ↔ 429 или 433 ↔ 431 в западном коридоре `x = 115`) алгоритм выявляет общую коридорную ось и соединяет аудитории напрямую через коридор крыла без спуска к главному коридору `y = 492`.
- **Вложенные помещения (Nested Rooms):**
  - Аудитории с входом через смежные помещения (например, 444 через 442, 433 через 431) снабжены массивом промежуточных транзитных вейпоинтов (`waypoints`). При выходе вейпоинты проходятся последовательно, при входе — в обратном порядке (`asReversed()`).
- **Межкрыльевая навигация:**
  - При переходе между перпендикулярными коридорами маршрут проходит через фиксированные узлы сопряжения (junctions): угол сопряжения восточного крыла `(902, 492)` или угол западного крыла `(115, 492)`.
- **Межэтажная навигация (Multi-Floor Routing):**
  - При перемещении между разными этажами (например, 4 этаж ↔ 3 этаж) алгоритм оценивает все 3 лестничные клетки (Западная, Центральная, Восточная) и вычисляет суммарную 2D-длину пешеходного пути на обоих этажах:
    $$\text{TotalDist} = \text{Dist}(\text{Room}_A \to \text{Stairs}_i) + \text{Dist}(\text{Stairs}_i \to \text{Room}_B)$$
    Выбирается лестница с минимальной суммой расстояний (например, для 421 → 301 автоматически выбирается Центральная лестница, для 401 → 301 — Восточная).
  - Генерируются два сегмента полилинии: `fromFloorPoints` (на исходном этаже) и `toFloorPoints` (на целевом этаже), а также точка перехода `transitionStairsName`.
- **Коллинеарное сглаживание (`simplifyRoutePoints`):**
  - Алгоритм удаляет промежуточные избыточные вершины полилинии на прямых отрезках с помощью критерия нулевой ориентированной площади треугольника:
    $$\text{Area} = (x_2 - x_1)(y_3 - y_1) - (y_2 - y_1)(x_3 - x_1)$$
    Если $|\text{Area}| < 1.0$, промежуточная точка отбрасывается. Все реальные ортогональные повороты (90°) гарантированно сохраняются.

### 6.5 Интерактивная визуализация этажей в Jetpack Compose
- **Одноэтажный режим (`SingleFloorInteractiveView`):**
  - Отображает схему выбранного этажа (3 или 4), подсвечивает аудитории, строит путь от двери к двери с бегущими шевронами.
- **Межэтажный связующий режим (`MultiFloorInteractiveView`):**
  - Отрисовывает оба этажа в едином виртуальном координатном пространстве (`1024 × 1368` px) со смещением нижнего этажа по оси Y.
  - Лестничные пролеты этажей соединяются анимированной пунктирной линией (`Color(0xFFD946EF)`, magenta) с пульсирующими маяками и информационным бейджем названия лестницы.
  - 100% точность хит-тестинга: клики по аудиториям на любом из двух этажей работают без искажений благодаря раздельному маппингу координат без 3D-деформации сетки.
